# 软件计算路径与GPU画像失配：小型机制验证方案

日期：2026年10月18日。对应主稿：《论文初稿_第二轮复审主稿修订_20261017.docx》。

本文件是待执行方案，没有产生新实验结果，也未连接云服务器、修改GPU设置或改动论文。

**推荐采用TF32设置切换实验：现有A100、T4及本机RTX 5070各运行同一组矩阵乘法，在软件中切换“允许／禁止TF32”，检查既有画像是否失配。** 本次方案已按三设备更新，与主稿硬件范围一致。云服务器是否开放功耗与频率控制尚不确定，因此本方案不依赖这些权限。新增正文控制在约半页至一页，以一张图和两段解释为主。

## 1. 只回答一个机制问题

在设备、矩阵尺寸和输入输出数据类型不变时，后端数学模式改变能否造成执行时间偏离？该作用是否依赖GPU能力及任务精度？

对应本文的问题是：现有上下文键包含任务族、规模、批量和dtype，但没有完整描述后端数学模式。软件执行设置变化，可能使同一上下文键对应不同耗时，导致画像失配。

PyTorch 2.5.1说明，allow_tf32控制是否允许在Ampere及以后设备上用TF32处理float32矩阵运算；该方式改变内部有效精度，输入输出仍可为float32。[PyTorch 2.5.1官方说明](https://github.com/pytorch/pytorch/blob/v2.5.1/docs/source/notes/cuda.rst#tensorfloat-32-tf32-on-ampere-and-later-devices)

**这是软件设置与硬件能力交互的诊断。不能将其写成历史实验全部偏差的归因，也不能预先宣布开启TF32必然产生某个加速比。**

## 2. 实验矩阵

| 项目 | 固定设置 |
|---|---|
| GPU | 原研究使用的A100、T4、RTX 5070，各1张；每张卡内部配对比较 |
| 主要任务 | 方阵GEMM：N=2048、4096、6144，输入输出FP32；均属于主稿已有上下文 |
| 任务对照 | N=4096的FP16 GEMM，同样属于已有上下文 |
| 唯一主动切换项 | 矩阵乘法的TF32许可模式；按已安装PyTorch版本选择对应接口，不混用新旧接口 |
| 固定项 | 每台机器内的PyTorch/CUDA/驱动、运算代码、输入矩阵、布局、计时范围、分配方式与其他数学设置 |
| 重复 | 每张卡3个测量轮次；每轮使用一个固定输入种子，同轮所有阶段复用相同矩阵 |
| 排除项 | 不启动调度器，不增加并发任务，不修改功耗或频率，不加载推理模型 |

A100与RTX 5070分别提供两个支持TF32的设备案例；T4不具备Ampere引入的TF32能力，因此提供架构对照。FP16任务提供任务类型对照。两个支持设备的响应幅度不必相同，两类对照是否接近无变化也以结果为准。[PyTorch设备支持说明](https://docs.pytorch.org/docs/2.9/notes/cuda.html#tensorfloat-32-tf32-on-ampere-and-later-devices)、[NVIDIA Ampere说明](https://developer.nvidia.com/blog/nvidia-ampere-architecture-in-depth/)、[NVIDIA Turing说明](https://developer.nvidia.com/blog/nvidia-turing-architecture-in-depth/)

现有材料记录A100、T4为PyTorch 2.5.1+cu124，RTX 5070为2.13.0+cu132，可优先沿用各自可用环境。执行前重新记录当前版本；不把历史环境记录当作当前环境证明，也不为这个实验强制统一或升级软件。主要证据是每张卡内部的设置切换效应，不能把不同卡之间的效应幅度差异全部归因于GPU架构，因为操作系统、框架与CUDA版本也可能不同。

## 3. 实施步骤

**准备。** 建立独立诊断脚本，复用原任务的torch.mm运算定义。输入在计时外生成并放置于GPU，固定连续布局，不使用autocast、torch.compile或额外并行流。每轮用同一组输入跨三个阶段重复，三个设备尽量使用相同CPU生成的输入与种子。固定并记录其他后端设置。本机5070测量期间避免运行游戏、视频处理或其他GPU计算，保留实际桌面运行环境的说明。

2.5.1环境显式设置并回读torch.backends.cuda.matmul.allow_tf32=False／True。对于5070的较新环境，先核对已安装版本支持的接口；若使用新版fp32_precision接口，则固定全局基准为ieee，只切换torch.backends.cuda.matmul.fp32_precision="ieee"／"tf32"，并回读生效设置。每个进程仅使用一套接口，不混用allow_tf32与fp32_precision；官方文档明确不支持混用。[PyTorch新版精度接口说明](https://docs.pytorch.org/docs/2.9/notes/cuda.html#tensorfloat-32-tf32-on-ampere-and-later-devices)

不要随后调用旧Worker初始化中的torch.set_float32_matmul_precision("high")覆盖诊断设置；不要将“允许TF32”自动当作已经证明某个具体Tensor Core内核被执行。检查是否存在覆盖TF32行为的环境设置，相关设置保持不变并记录。

**每轮采用三阶段，检查切换及恢复。**

| 轮次 | 阶段1 | 阶段2 | 阶段3 |
|---|---|---|---|
| 1 | 禁止TF32 | 允许TF32 | 恢复禁止TF32 |
| 2 | 允许TF32 | 禁止TF32 | 恢复允许TF32 |
| 3 | 禁止TF32 | 允许TF32 | 恢复禁止TF32 |

每个阶段执行上述四个上下文。同一轮的上下文顺序固定，轮次之间采用预先记录的不同顺序。每轮重新启动测量进程，记录轮次开始时间。三个轮次是少量重复测量，不代表三个独立硬件环境。

每个“阶段×上下文”先预热至少20次且持续至少3秒，预热不计入结果；随后记录20个计时窗口。每个窗口连续执行10次相同GEMM，用CUDA Event测量整个窗口，结束事件同步后除以10，得到每次GEMM的平均时间。所有设置使用相同窗口定义。20个窗口用于描述本轮稳定性，不把其中200次GEMM当作200个独立样本。该重复窗口是新增诊断的测量单位，不与历史单任务耗时直接拼接。

完整计划为3设备×4上下文×3轮×3阶段×20窗口，共2160条计时记录，比原两设备方案新增720条5070记录。执行前只做一次接口及输出检查；不要依据预试验是否“有显著差异”来重选矩阵尺寸或数学模式。

计时范围不包括输入生成、主机到GPU复制、日志写入或服务器通信。CUDA操作具有异步性，采用事件与同步计时是必要的。[PyTorch CUDA计时说明](https://github.com/pytorch/pytorch/blob/v2.5.1/docs/source/notes/cuda.rst#asynchronous-execution)

如能只读获取GPU频率、温度、功耗及活动进程，可在测量之外低频记录，用于发现明显漂移或外部干扰；不把这些读数解释成独立因果证据。保留全部有效计时，不按快慢删点。若发生任务失败、外部作业介入或恢复阶段明显不稳定，保留该轮记录并标注原因；不要无说明地用重跑结果替换。

## 4. 三个结果量足够

**（1）设置切换引起的耗时比。**

每个阶段先取20个窗口的中位数。某设置在本轮出现两次时，对这两个阶段中位数取几何平均；只出现一次时直接使用其阶段中位数。由此得到本轮的T_off与T_on，计算：

R = T_off / T_on。

R>1表示允许TF32的测量更快。若把允许TF32时的测量作为画像、实际运行变为禁止TF32，则旧画像对实际耗时的相对低估为1−1/R（仅在R>1时这样表述）。反方向切换会造成相反方向的预测偏差。正文主要报告R即可，不必另加误差指标表。

对每个上下文画出3轮R及其中位数，保留跨轮波动。无需为了这组探索性实验添加大量显著性检验，也不从20个同轮窗口构造看似精确的独立样本推断。

**（2）恢复程度。**

比较阶段3与阶段1的中位耗时比。两阶段设置相同，恢复接近1且各轮模式一致，会增强对设置影响的解释；若恢复漂移与切换效应相当，则应报告混杂仍然明显，不能作清晰归因。无需事后挑选一个让结论通过的恢复阈值。

**（3）输出数值差异。**

在计时外保存同一输入下两种设置的输出，计算相对Frobenius差异：

delta = ||C_on − C_off||_F / ||C_off||_F。

将C_off作为比较参考，不称其为数学真值。报告输出是否有限及delta即可，不需要开展应用准确率实验。这项检查是为了明确：输入输出dtype同为FP32，不等于内部计算精度完全相同；本实验不证明两种设置在所有应用中可无条件互换。

## 5. 结果如何解释

| 实际观察 | 可以支持的解释 |
|---|---|
| A100或5070的FP32任务随设置切换发生稳定变化，恢复良好；T4与FP16对照变化较小 | 与数学模式和硬件支持共同影响性能的机制一致；仅用dtype记录画像可能不足。只在一个设备成立时，将结论限定于该设备和环境 |
| 同一设备三个FP32尺寸同向，但幅度不同 | 设置可产生跨上下文共同偏移，同时保留规模依赖；不能据此断言同一任务族适用统一倍率 |
| A100与5070的效应幅度不同 | 报告两个所测环境的差异；不能在软件栈不同的条件下单独识别架构效应 |
| 所有设备和精度都同幅度漂移，或恢复失败 | 可能存在热状态、外部负载等共同变化，当前实验不足以隔离设置作用 |
| 允许／禁止设置没有形成可重复差别 | 如实报告本配置下未检出清楚的性能差异；先核查设置是否生效，不为了“做出效果”反复换条件 |

任务名compute不等于已证明计算瓶颈；没有内核计数器时，使用“与TF32计算路径解释一致”，不声称已直接测量Tensor Core利用率。本小实验默认不要求Nsight剖析。

## 6. 与现有论文的连接方式

建议在第5.6节现有历史画像迁移描述之后增加一个短段，标题可为“软件计算路径变化的诊断案例”。第4.1节用一两句交代实验设计，完整步骤放补充材料。正文保留一张小图：三个GPU面板，横轴四个上下文，纵轴R，展示三个轮次及中位数，R=1为参考线；恢复比和输出差异放补充表。仍以半页至一页为目标，不新增调度实验或扩大任务种类。

建议讨论限定为三点：

1. 相同GPU、规模和dtype并不能完整规定执行性能，后端数学模式是一个可测的画像有效性条件。
2. 不同设备与上下文对同一设置的响应可能不同，为比较共享修正与局部修正提供机制动机；本实验本身不验证PoolEMA或Full的优劣，也不测定模拟共享比例rho。
3. 已知设置应优先写入画像元数据或触发重新画像。在线校准用于处理仍存在或尚未被完整记录的偏差，不能据此宣称必须用校准替代显式配置管理。

不能将新实验作为历史两批部署的原因追溯，也不能把已有71.72%的描述性占比重新解释成TF32的贡献。此处只补充一种受控、可解释的画像失配来源。

结果出来后可按事实填入以下写作框架，不提前填入方向或数值：

> 为检验软件计算路径变化对画像有效性的影响，在A100、T4和RTX 5070上固定输入矩阵、任务规模及输入输出dtype，在各设备内仅切换矩阵乘法的TF32许可设置，并在三个测量轮次中交替切换、恢复。图X显示，[实际耗时比及恢复结果]；[对照结果]。该结果[支持／尚不足以支持]软件数学模式与设备能力的交互可使固定画像发生偏离。由于TF32改变内部计算精度，同时报告输出差异。不同设备的软件环境并非完全一致，因此跨设备效应幅度不作单独的架构归因。该案例不用于归因历史部署偏差，也不构成某种校准策略普遍优越的证据。
